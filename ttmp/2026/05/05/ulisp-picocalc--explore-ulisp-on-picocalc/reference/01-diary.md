# Diary

## Goal

Explore, compile, and ultimately run uLisp on the Clockwork Pi PicoCalc handheld computer. Document the full build process and create reusable scripts.

## Step 1: Research and Source Gathering

Researched uLisp and PicoCalc to understand the ecosystem. The PicoCalc is a handheld computer by Clockwork Pi based on an RP2040 Raspberry Pi Pico, with a 320x320 IPS display, QWERTY keyboard, and SD card slot. uLisp is a Lisp interpreter for microcontrollers by David Johnson-Davies (technoblogy). There's a dedicated `technoblogy/ulisp-picocalc` repo that is the PicoCalc-specific fork — no need to use `ulisp-arm` + manual patching.

### Prompt Context

**User prompt (verbatim):** "Create a new docmgr to explore ulisp on the picocalc. First, try to compile it. Keep a diary. Store all the scripts that you write in the scripts/ directory of the ticket. Use `surf kagi search --query ...` if you need to search the web."

**Assistant interpretation:** Create a docmgr ticket workspace, research uLisp for PicoCalc, compile it, keep a diary, and save scripts in the ticket's scripts/ directory.

**Inferred user intent:** Get a working uLisp build for the PicoCalc, with full documentation of the process for future reference and reproducibility.

### What I did

- Created docmgr ticket `ulisp-picocalc` with tasks and docs
- Searched the web with `surf kagi search` to find the official repos and build instructions
- Downloaded 7 source documents to `sources/` using defuddle (uLisp main page, PicoCalc machine doc, build instructions, forum threads, benchmarks)
- Cloned `technoblogy/ulisp-picocalc` repo (the dedicated PicoCalc version, not `ulisp-arm`)
- Also cloned `clockworkpi/PicoCalc` for reference (contains the older patch-based approach)

### Why

The `technoblogy/ulisp-picocalc` repo is the author's dedicated PicoCalc version — it's the already-patched, ready-to-compile source. The `clockworkpi/PicoCalc` repo has a patch-based approach against `ulisp-arm` v4.5a, but the dedicated repo is cleaner and more current.

### What worked

- Found the exact build requirements: Arduino IDE with `arduino-pico` core, `TFT_eSPI 2.5.34` (patched), and `arduino_picocalc_kbd` library
- All web searches returned highly relevant results — uLisp PicoCalc is well-documented

### What didn't work

- Initially cloned `ulisp-arm` and applied the ClockworkPi patch (following older instructions). User correctly pointed out this was unnecessary since the dedicated repo exists.

### What I learned

- The PicoCalc has a separate STM32 processor for the keyboard, communicating via I2C — that's why the `arduino_picocalc_kbd` library is needed
- uLisp on PicoCalc includes graphics extensions, SD card support, sound (note function), ARM assembler, and custom functions like `get-key`, `read-pixel`, `save-bmp`
- BIOS 1.4 keyboard firmware has incompatibilities with current uLisp — only BIOS 1.2 is fully supported
- The display is an ILI9488, driven via TFT_eSPI with a custom setup file `Setup60_RP2040_ILI9488.h`

### What was tricky to build

Nothing tricky in this step — straightforward research and source gathering.

### What warrants a second pair of eyes

### What should be done in the future

### Code review instructions

## Step 2: Set Up Build Toolchain and Compile

Installed `arduino-cli` v1.4.1, the RP2040 core v5.6.0 (latest), TFT_eSPI 2.5.34 (patched with PicoCalc display setup), and the keyboard library. Compiled uLisp successfully, producing a 460KB UF2 image.

### Prompt Context

**User prompt (verbatim):** (see Step 1)

**Assistant interpretation:** Set up the full Arduino toolchain headlessly via arduino-cli and compile uLisp for the RP2040-based PicoCalc.

**Inferred user intent:** Get a working .uf2 binary that can be flashed to the PicoCalc.

### What I did

- Installed `arduino-cli` v1.4.1 via the official install script
- Configured `arduino-cli` with the `arduino-pico` board manager URL
- Installed `rp2040:rp2040` core v5.6.0 (latest; docs tested with v4.5.0)
- Installed `TFT_eSPI` v2.5.34 via `arduino-cli lib install`
- Patched `TFT_eSPI/User_Setup_Select.h`: commented out `User_Setup.h`, added `Setup60_RP2040_ILI9488.h`
- Copied `Setup60_RP2040_ILI9488.h` to `TFT_eSPI/User_Setups/`
- Cloned `arduino_picocalc_kbd` to `~/Arduino/libraries/`
- Created sketch directory with the .ino file
- Wrote `scripts/01-compile-ulisp-picocalc.sh` build script
- Compiled successfully with `arduino-cli compile --fqbn rp2040:rp2040:rpipico`

### Why

Using `arduino-cli` instead of the Arduino IDE GUI enables reproducible headless builds and scripting. The build script is stored in the ticket's `scripts/` directory for future use.

### What worked

- Build completed with only harmless warnings:
  - `TOUCH_CS pin not defined` — expected, PicoCalc has no touchscreen
  - `variable 'result' might be clobbered by 'longjmp' or 'vfork'` — known uLisp pattern with setjmp/longjmp error handling
- Output: `ulisp-picocalc-sketch.ino.uf2` at 460,800 bytes (452K)
- Pre-built reference from technoblogy: 465,920 bytes (456K) — very close, slight difference from different core versions

### What didn't work

- `--build-cache-path` flag is deprecated in arduino-cli 1.4.1 (non-fatal)

### What I learned

- `arduino-cli` is much more convenient than the old Arduino IDE 1.8.5 for headless builds
- The RP2040 core v5.6.0 compiles uLisp fine despite the docs testing with v4.5.0
- Memory usage: 211,448 bytes (10%) program, 193,800 bytes (73%) dynamic memory
- The build uses 73% of the RP2040's 264KB RAM — that's the Lisp workspace

### What was tricky to build

- Getting the TFT_eSPI patching right: must both copy the setup file AND modify `User_Setup_Select.h`. Missing either step causes compilation errors about the display driver.
- The sketch directory name must match the .ino filename for Arduino compatibility.

### What warrants a second pair of eyes

- The 73% dynamic memory usage seems high — verify this leaves enough room for the Lisp workspace (should be ~68KB for local variables)
- The core version mismatch (5.6.0 vs tested 4.5.0) — test on hardware to confirm no regressions

### What should be done in the future

- Flash the UF2 to the PicoCalc and verify it boots
- Test keyboard, display, SD card, and basic Lisp evaluation
- Benchmark against the reported uLisp 4.7b numbers from the forum

Research led to `ulisp-wasm` by Eliot Akira — a C99 port of uLisp that compiles natively with clang/gcc. Built a 349 KB native binary in one command. Running interactively in tmux session `ulisp`. Wrote design doc and uploaded to reMarkable.

### Prompt Context

**User prompt (verbatim):** "I want to run a version compiled for my host linux pc, is there something like that, and if not, how to build it. Make a new research / design document."

**Assistant interpretation:** Find or create a native Linux build of uLisp for local development and testing, and document the process.

**Inferred user intent:** Have a fast local uLisp REPL for developing and testing Lisp code before flashing to PicoCalc hardware.

### What I did

- Searched web with `surf kagi search` for "uLisp native Linux POSIX compile desktop"

- Built native binary with `clang -std=c99 -lm -O3` — zero warnings, 349 KB output

- Launched interactive REPL in tmux session `ulisp`
- Wrote `scripts/02-build-ulisp-native-linux.sh` build script

### Why

The native build enables a fast develop-test cycle without hardware. Same Lisp core as PicoCalc, just without the hardware-specific extensions.

### What worked

### What was tricky to build

## Step 5b: Fix Forward Declaration Resolution (pserial, pln, indent, printstring)

The initial `c_cpp_properties.json` resolved library headers but CLion couldn't resolve functions like `pserial`, `pln`, `indent`, `printstring` that are defined in the same `.ino` file but used before their definition. The root cause: Arduino's `.ino` preprocessor auto-generates forward declarations that CLion doesn't see.

### What I did

- Analyzed the preprocessed `build/sketch/ulisp-picocalc-sketch.ino.cpp` and discovered that Arduino inserts 925 lines of `#line N` + prototype pairs before the first function body
- Wrote `scripts/04-extract-forward-declarations.py` to extract the minimal 36 needed prototypes into `_ulisp_fwd_decls.h`
- Updated `scripts/03-generate-c_cpp_properties.py` to call the extraction and add the header as `forcedInclude` in the configuration
- Regenerated `.idea/c_cpp_properties.json` with the forced include
- Verified `pserial`, `pln`, `indent`, `printstring`, `setup`, `loop` are all in the forward declarations

### Why

Arduino `.ino` files don't need forward declarations because the builder scans for all function signatures and inserts prototypes at the top. CLion parses the raw `.ino` without this preprocessing, so every forward reference is unresolved. The `forcedInclude` in `c_cpp_properties.json` tells CLion's IntelliSense to always include the extracted declarations.

### What worked

- The preprocessed `.cpp` has exactly the right prototypes — just extract and reuse them
- `forcedInclude` in `c_cpp_properties.json` is the clean CLion mechanism for this

### What was tricky

- The forward declarations are interleaved with `#line` directives and blank lines — had to parse the block correctly by detecting the pattern of `#line` + `prototype;` and stopping at the first `{` (function body)

### Code review instructions

- Run `scripts/03-generate-c_cpp_properties.py` and verify `_ulisp_fwd_decls.h` contains `void pserial(char c);` etc.
- Check `.idea/c_cpp_properties.json` has `forcedInclude` pointing to the header

## Step 5: CLion IntelliSense Configuration (c_cpp_properties.json)

Set up `.idea/c_cpp_properties.json` so CLion's C++ IntelliSense can find all Arduino/RP2040 library headers (`LittleFS.h`, `TFT_eSPI.h`, `hardware/pwm.h`, `PCKeyboard.h`, etc.) and resolve symbols correctly for the cross-compilation target.

### Prompt Context

**User prompt (verbatim):** "Setup .idea/c_cpp_properties.json so that @ulisp-picocalc/ finds the arduino library headers such as LittleFS.h and TFT_eSPI.h and hardware/pwm.h and all that. maybe arduino-cli can help? Keep a diary in ttmp/2026/05/05/ulisp-picocalc--explore-ulisp-on-picocalc/. save scripts in the scripts/ folder of the ticket."

**Assistant interpretation:** Configure CLion's C++ IntelliSense by generating `c_cpp_properties.json` with correct include paths, defines, and compiler settings extracted from the actual arduino-cli build output.

**Inferred user intent:** Make CLion useful as a code browser/navigator for the uLisp PicoCalc source, with no red squiggles on Arduino/RP2040/PicoCalc-specific headers.

### What I did

- Analyzed `build/compile_commands.json` (produced by arduino-cli) to extract all `-I` include paths, `-D` defines, and `-iprefix` settings
- Read `build/sketch/ulisp-picocalc-sketch.ino.cpp.d` (dependency file) to verify all transitive header dependencies are covered
- Discovered that arduino-cli uses `@file` response files and `-iprefix` to pull in ~100+ pico-sdk header directories — CLion doesn't understand these, so they must be expanded explicitly
- Wrote `scripts/03-generate-c_cpp_properties.py` — a Python script that:
  - Parses `compile_commands.json` for `-I`, `-D`, `-iprefix`, and `@file` entries
  - Walks the pico-sdk tree to discover all `*/include` directories (for `hardware/pwm.h`, `pico/time.h`, etc.)
  - Adds project-local source directories (`ulisp-picocalc-sketch/`, `ulisp-picocalc/`)
  - Adds lwip include directories
  - Outputs a complete `c_cpp_properties.json` with 181 include paths and 105 defines
- Ran the script to generate `.idea/c_cpp_properties.json`
- Verified all critical headers resolve: LittleFS.h ✓, TFT_eSPI.h ✓, hardware/pwm.h ✓, Arduino.h ✓, PCKeyboard.h ✓, SPI.h ✓, SD.h ✓

### Why

CLion uses `c_cpp_properties.json` (or `compile_commands.json` with CMake) for its IntelliSense engine. Since this is an Arduino project with no CMake, the properties file is the right way to configure includes/defines. The arduino-cli build already produces a `compile_commands.json`, but CLion's parser doesn't handle the `@file` response files or `-iprefix` tricks used by the RP2040 core — so a dedicated generator that expands those is needed.

### What worked

- Using `compile_commands.json` as the source of truth was the key insight — it captures the exact flags from a real build
- Walking the pico-sdk tree for all `include` directories ensures complete coverage without having to hardcode paths
- The generated file resolves all 7 critical headers checked

### What didn't work

- Initially had the wrong number of `..` in the script's default `project_dir` calculation (5 instead of 6 levels up from `scripts/`)

### What I learned

- The RP2040 arduino core uses `-iprefix` + `@file` response files extensively — these are standard GCC features but CLion's IntelliSense parser ignores them
- The pico-sdk has ~100 `include` directories spread across `rp2040/`, `rp2_common/`, `common/`, and `boards/` subtrees
- `compile_commands.json` is the single best source of truth for build configuration in Arduino projects

### What was tricky to build

- The path from `ttmp/2026/05/05/ulisp-picocalc--explore-ulisp-on-picocalc/scripts/` to the project root is 6 levels, not 5 — easy to miscount
- The `@file` response files (`platform_def.txt`, `platform_inc.txt`, `core_inc.txt`) contain additional `-I` and `-D` flags that must be parsed
- The `-iprefix` mechanism means the compiler implicitly searches hundreds of subdirectories — for CLion, each one must be explicitly listed

### What warrants a second pair of eyes

- The 181 include paths might include some unnecessary ones (lwip internals, etc.) — this won't cause errors but adds lookup time
- The defines include some with `=` values containing `//` (like `CYW43_WARN=//`) — CLion should handle these but worth checking

### What should be done in the future

- Re-run `03-generate-c_cpp_properties.py` after updating the arduino-pico core version (the paths include version numbers like `5.6.0`)
- Consider adding a `compile_flags.txt` alongside for clangd-based tools
- Test that Go-to-Definition works in CLion for key types like `TFT_eSPI`, `LittleFS`, `PCKeyboard`

### Code review instructions

- Check `scripts/03-generate-c_cpp_properties.py` for the generation logic
- Verify `.idea/c_cpp_properties.json` has `"name": "ulisp-picocalc"` configuration selected in CLion
- In CLion: File → Settings → Build → Compilation Database → ensure it picks up `build/compile_commands.json`
